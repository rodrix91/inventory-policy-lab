# Contributing

Project status: alpha, maintained by Rodrigo Pantoja Navajas ([@rodrix91](https://github.com/rodrix91)). Small, focused changes with tests are welcome; for a new method or a change in a formula, open an issue first with a reference.

## Setup

Requires Python 3.11+. From the repository root:

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install --require-hashes -r requirements-dev.lock   # exact pins + hashes (or: pip install -r requirements-dev.txt)
pip install -e .                      # optional: only for the `inventory-policy-lab` command
```

The tests do not need `pip install -e .` (pytest puts `src/` on the path and subprocess tests set `PYTHONPATH=src`). Run all commands from the repository root.

## Checks (run all before opening a PR)

```bash
python -m pytest                 # tests
coverage run -m pytest && coverage combine && coverage report   # 100% line + branch coverage (CI enforces it)
ruff check .                     # lint
ruff format --check .            # formatting, also of the Python block in README.md (`ruff format .` fixes it)
mypy                             # strict type check of src, tests and scripts
python -m build                  # sdist + wheel into dist/ (downloads the pinned setuptools)
```

Build from a clean clone, not from a working directory with stray files: the sdist is assembled from what is on disk. CI also builds the sdist and runs the tests from the unpacked archive (job `sdist`); when a test starts reading a new file, make sure `MANIFEST.in` ships it.

## Generated files

Three files are generated by scripts and checked by the tests and by CI. After a change that affects them, regenerate and review the diff:

| File | Script |
|---|---|
| `examples/demand_synthetic.csv` (synthetic data, seeded) | `python scripts/generate_example.py` |
| `docs/abc-pareto.svg` | `python scripts/make_pareto_svg.py` |
| Output samples in `README.md` | `python scripts/update_readme_samples.py` |

Each script accepts `--check` to only report. Never edit a README sample by hand: it must be the output of a real run.

The worked example (`examples/worked_example.csv`) is different: its expected numbers are derived by hand in the docstring of `tests/test_worked_example.py`. If a change moves one of them, the change needs a written justification in the PR, and the docstring derivation must be updated to match.

## Guidelines

- Runtime code stays standard-library only. Dev tools go in `requirements-dev.txt`; after changing them, regenerate the hashed lock with [uv](https://docs.astral.sh/uv/): `uv pip compile requirements-dev.txt --generate-hashes --universal --python-version 3.11 -o requirements-dev.lock`.
- Every behavior change comes with tests. Formulas get a test with numbers worked out by hand, not only numbers copied from a run.
- Cite the source of any new method or formula in the README "Methods" section.
- Record decisions that shape the design in `docs/decisions/` (one ADR per decision).
- Keep type hints on all functions; keep modules small and the data flow one-way (see ADR 0001).
- Use small commits and honest messages; never commit secrets or real company data.

## Dependency updates (Dependabot)

Dependabot opens weekly PRs for the pinned dev tools. It edits `requirements-dev.txt` but may not regenerate the hashed lock, so do not merge one as is: regenerate `requirements-dev.lock` on the PR branch with the `uv pip compile` command above, and merge only when CI passes on Python 3.11, 3.12 and 3.13.

## Releases

1. In a PR, bump the version in `pyproject.toml` and `src/inventory_policy_lab/__init__.py`, and turn `[Unreleased]` in `CHANGELOG.md` into `## [X.Y.Z] - YYYY-MM-DD` with its link at the bottom. `tests/test_version.py` fails if the version has no CHANGELOG section.
2. After the merge, tag `vX.Y.Z` on `main` (`git tag vX.Y.Z && git push origin vX.Y.Z`) or publish a release with that new tag from the GitHub releases page.
3. The `Release` workflow checks that the tag matches the package version, builds the sdist and the wheel, runs the tests from them and attaches both to the GitHub release, with the CHANGELOG section as notes (`python scripts/release_notes.py X.Y.Z`). Nothing is published to PyPI.
